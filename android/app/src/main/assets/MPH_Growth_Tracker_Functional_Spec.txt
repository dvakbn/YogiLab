MPH GROWTH TRACKER
FUNCTIONAL / CONTENT / DATA SPECIFICATION FOR A REDESIGN
Source of truth: current standalone HTML application after removing Books and Daily Intelligence.

IMPORTANT SCOPE
================
This document describes function, content, storage, navigation, calculations, reminders, backup, and question-paper data only.
Do NOT copy the old visual styling, component appearance, color choices, spacing, typography, card design, layout styling, or animation behavior.
The redesign may completely replace the UI and animation while preserving the functional contract below.
Books and Daily Intelligence are intentionally removed from the app.

1. APPLICATION ARCHITECTURE
============================
- One self-contained HTML document.
- Plain HTML + CSS + vanilla JavaScript. No React, Vue, Angular, Bootstrap, Tailwind, or other frontend framework is required by the current app.
- No application backend is present in the current implementation.
- Data is primarily persisted in browser localStorage.
- The app behaves like a single-page app for navigation, but the views are rendered dynamically into a central detail area.
- Main dashboard cards use data-open values. Opening a card changes History API state and renders a detail view instead of navigating to a separate HTML document.
- Question-paper reader is another in-app state and the PDF viewer is a separate history state.
- Existing PDF files are expected to be available by filename relative to the HTML document.
- The app must remain usable without a server-side application database; localStorage is the persistence layer.

2. MAIN DASHBOARD: CARDS THAT REMAIN
=====================================
The main dashboard contains these functional destinations in the current order:
1) Parameters
2) To-Do
3) Affirmations
4) Question Papers
5) IIPHG Syllabus
6) Reviews
7) Settings

Reviews and Settings are rendered as two separate actionable destinations inside the final dashboard row.

Removed completely:
- Books
- Daily Intelligence

3. GLOBAL DATE / TIME BASICS
=============================
- TODAY is a YYYY-MM-DD string generated from the browser's current local Date.
- dateMinus(n) shifts the local calendar date by n days.
- The app uses the user's local browser date/time for daily calculations.
- Week keys are derived from the configured weekly-check weekday.
- The default weekly-check day is Sunday (numeric day index 0).
- The default streak threshold is 3 missed days.

4.2 DAILY VALUE TYPES
----------------------
Built-in field types:
- bool: exact boolean true/false.
- boolNote: object with done:true/false and optional note string.
- seg3: one enumerated choice.
- chips: one enumerated choice.
- chipsMulti: array of selected strings.
- text: free-form string.
- condText: free-form string shown conditionally; not part of completion total.
- link: internal navigation link type exists in the renderer contract, but no remaining built-in parameter currently depends on it.

A field is considered filled as follows:
- bool: true or false both count as answered.
- boolNote: object with done true or false counts as answered.
- seg3/chips: a truthy stored value counts.
- chipsMulti: non-empty array counts.
- text: trimmed non-empty string counts.
- custom numeric/text/etc. use customValueFilled rules below.

4.3 DAILY PROGRESS
-------------------
For each day and each built-in section:
- Exclude condText and link fields from totals.
- Exclude hidden parameters from totals.
- Every custom parameter adds one total.
- A custom parameter counts done when its value satisfies its type-specific filled rule.
- Section progress = done / total.
- Overall parameter completion = sum of all section done values / sum of all section totals.
- This produces the percentage shown in History and used by Reviews.

4.4 STREAKS
------------
Some built-in boolean fields have a streak marker enabled.
The streak function walks backward from the selected day and counts consecutive days where that field is not true.
Streak logic recognizes bool true and boolNote objects with done:true as true.

The “needed attention” logic checks boolean/boolNote fields and flags a field when its missed streak is greater than or equal to SETTINGS.streakFlagDays.
The missed-streak scan is capped at 90 days and at the age of the earliest stored record.

4.5 CUSTOM DAILY PARAMETERS
-----------------------------
Storage key: mph_custom_v1
Structure: object keyed by built-in card ID, each value is an array of custom definitions.
A custom definition contains at minimum:
- id
- label
- type
Optional:
- placeAfter
- options (for choice type)

Available custom types:
- yesno
- rating (1–5)
- number
- emoji/mood
- choice
- text

For choice type, options are comma-separated by the user; if none are given, default options are Option 1 and Option 2.
Daily custom values are stored inside mph_records_v1 under the key custom_<customId> inside the owning card/date record.

The Daily Parameters page has “Add your own parameter”.
The user chooses:
- where it should appear (section placement)
- answer type
- optional comma-separated choices

Custom fields can be deleted. Deleting a custom field also removes the matching custom_<id> value from the selected date's record.

5. PARAMETERS: WEEKLY MODE
===========================
Weekly data is stored by a week key.

Built-in weekly fields:
- Revise all major topics this week
  key: reviseAll
  type: bool
- Review research papers read
  key: reviewPapers
  type: bool
- Review skill progress
  key: reviewSkills
  type: bool
- Organize notes
  key: organizeNotes
  type: bool
- Check pending assignments
  key: checkAssignments
  type: bool
- Plan next week
  key: planNextWeek
  type: boolNote

Weekly storage keys:
- mph_weekly_v1 = object keyed by week key, then field key -> value.
- mph_weekly_custom_v1 = array of weekly custom definitions.

Weekly custom parameters use the same conceptual custom types as daily parameters.
The Weekly page supports adding a custom weekly parameter, editing it, and deleting it.

Weekly progress counts built-in visible weekly fields plus all weekly custom fields.
A bool is done when true or false has been explicitly selected.
A boolNote is done when done:true or done:false exists.
A custom value is done according to customValueFilled.

Week calculation:
- The start day is SETTINGS.weeklyCheckDay.
- weekKey(0) is the current configured week.
- negative offsets access past weeks.
- positive offsets represent future week keys for navigation but the UI prevents moving beyond the current week.

6. PARAMETERS: HISTORY MODE
============================
History is a month calendar based on the browser's current month.
Behavior:
- Shows all dates in the selected month.
- Future dates are disabled.
- Past/current dates can be selected.
- Each date can show an activity dot if there is recorded activity.
- Each date can show that day's completion percentage.
- Selecting a date switches back to Daily mode for that date.
- Previous months can be viewed.
- Future months are blocked from being selected beyond the current month.

7. TO-DO CARD
=============
Storage key: mph_todos_v1
Value shape: object keyed by YYYY-MM-DD, each value is an array of items.
Each item is:
- id
- text
- status
Status values used by the current implementation:
- null (not yet marked)
- done
- missed

Current page behavior:
- It displays a section labeled “Yesterday's list” backed by TODOS[TODAY] in the existing source.
- It displays a section labeled “Tomorrow's plan” backed by TODOS[TOMORROW].
- Tomorrow tasks can be added with free text.
- Tomorrow tasks can be deleted.
- Items in the TODAY-backed list can be marked Done or Missed.
- Clicking the already-selected status toggles that status back to null.
- No separate task-edit operation exists; the current code supports add, status toggle, and delete.

Dashboard summary:
- If nothing exists in today's/tomorrow's data, shows Nothing planned.
- Otherwise displays the number planned for tomorrow.

Important redesign note:
Preserve the stored data semantics unless deliberately migrating them. The existing code's “Yesterday's list” label maps to TODOS[TODAY].

11. REVIEWS CARD
=================
Reviews is derived from stored Parameters, To-Do, and Affirmations data. It does not have its own persistence key.

Current review period is initialized as “week”.
Supporting calculations include:

A) Category percentage
For each category and a requested date range:
- visible built-in fields excluding condText/link
- plus all custom fields
- numerator = filled answers
- denominator = total answer slots
- rounded percentage

B) Earliest stored record
The earliest date key present in mph_records_v1 is used as a lower bound for missed-streak scanning.

C) Subject summary
Reads the Subject Revision multi-select over a date range.
Counts each selected subject.
Reports the most-used subject and least-used subject.
If none have been selected, returns “No subjects logged yet”.

D) On-time percentage
Used for seg3 fields where the value equals “onTime”.

E) Affirmation count
Counts all affirmation strings across the requested number of past days.

F) To-Do completion percentage
Across the requested days, counts all stored todo items and the subset with status done.
Returns null when there are no items.

G) Strongest category / weakest category
Compares category percentages.
These are used to create narrative suggestions.

H) Field breakdown
For bool and boolNote fields, counts days where the field is true.

I) Attention flags
Fields meeting the missed-streak threshold are surfaced as needing attention.

J) Weekly rhythm / pattern view
The current implementation looks at the last 7 days and derives:
- active days
- day-by-day completion percentage
- early-week average (first three points with activity)
- recent average (last three points with activity, excluding the final point by current slicing convention)
- delta
- trend label
- consistency based on standard deviation bands
- biggest category movement
- most frequently selected subject
- number of days with affirmations
- To-Do completion percentage

Narrative outputs include:
- active-day summary
- strongest/weakest section
- movement across the week
- study focus
- affirmations pattern
- To-Do pattern

No separate review data is stored; reviews are recalculated from source data whenever rendered.

13. ON-SCREEN REMINDER SYSTEM
=============================
There is a lightweight in-app reminder area on the main page.
This is not a browser push-notification service and is not an OS notification system.

Daily reminder behavior:
- Eligible from 8:30 PM local time onward.
- Only shown when today's parameter completion is incomplete.
- Message: Daily check-in / Take a moment to finish today’s parameters.
- Clicking the reminder opens Parameters.
- The close button dismisses the reminder.
- Dismissal key: mph_reminder_daily_YYYY-MM-DD
- Once dismissed, it does not reappear for that date.

Weekly reminder behavior in the source:
- Intended as a weekly check reminder after 8:30 PM on the configured weekly day.
- It is currently hard-coded to Sunday in renderReminders and should be corrected to SETTINGS.weeklyCheckDay for the redesign.
- It is shown only when weekly progress is incomplete.
- Message: Weekly check-in / Review and complete your weekly parameters.
- Clicking opens Parameters.
- Dismissal key: mph_reminder_weekly_<selectedWeekKey>
- Once dismissed, it stays dismissed for that week.

Rendering frequency:
- renderReminders() is called when the dashboard renders.
- It is called every 30 seconds afterward, so crossing 8:30 PM while the app remains open can make the banner appear without a full page reload.

No browser Notification API, service worker, push token, or mobile OS scheduling is present in the current implementation.

====================================================
For the redesigned app, the “Add to Google Calendar” action should:
1) Calculate the next occurrence of SETTINGS.weeklyCheckDay at exactly 8:30 PM local time.
2) Create a 30-minute event.
3) Use the browser's resolved IANA timezone.
4) Use Google Calendar's event-template URL.
5) Add:
   title = Weekly Check
   description = MPH Growth Tracker weekly check-in
   recurrence = weekly on the configured weekday
6) Open the Google Calendar URL directly in a new browser tab/window.

8) The optional ICS action may remain only as a secondary export/compatibility option.

15. NAVIGATION / HISTORY API CONTRACT
=====================================
The app uses browser History API states with mphTracker=true.

State examples:
Home:
{mphTracker:true,mphView:'home',currentCard:null,currentPaper:null}

Regular card:
{mphTracker:true,mphView:'<cardId>',currentCard:'<cardId>',currentPaper:null}

Paper:
{mphTracker:true,mphView:'paper',currentCard:'papers',currentPaper:'<filename>'}

PDF:
{mphTracker:true,mphView:'pdf',currentCard:'papers',currentPaper:'<filename>',pdfFilename:'<filename>',pdfTitle:'<title>'}

Hash forms:
#home
#view=<cardId>
#paper=<encoded filename>
#pdf=<encoded filename>&title=<encoded title>&card=<encoded card>&paper=<encoded paper>

Routing operations:
- navigateTo(view) uses history.pushState and then renders the destination.
- setAppRoute(state,false) creates a new entry.
- replace mode can update the current entry without pushing.
- stateFromLocation reconstructs state from history.state or the hash.
- applyViewState renders the state.

Back behavior:
- The Back button calls history.back() when an app-owned history state exists.
- PDF Back returns to the underlying paper through a dedicated history entry.
- Android Chrome Back/swipe-back is handled by popstate.
- If an unexpected non-app history entry is exposed, the code installs a safe home state.

The redesigned UI may be completely different, but the same semantics should be preserved so browser Back behaves naturally.
